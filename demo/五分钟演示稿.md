# 五分钟演示稿（目标 4 分 30 秒）

说话保持自然，不需要逐字背诵。正式录制前至少完整排练两遍，并把总时长控制在 4 分 20 秒到 4 分 40 秒，给停顿和误操作留余量。

## 0:00–0:30｜项目动机

画面：标题或仓库首页。

口播：

> 大家好，我介绍的作品是一个用 C++17 编写的跨平台远程桌面原型。做它的原因，是我想把网络传输、图像处理、桌面输入以及 Windows 和 Linux 平台 API 串成一个完整的工程闭环，而不是只写一个单点功能。项目包含 Windows 和 Linux 的服务端与客户端，四种组合使用同一套通信协议。

## 0:30–1:05｜架构与数据流

画面：打开 `demo/architecture.svg`。

口播：

> 服务端负责捕获桌面。Windows 使用 GDI，Linux 使用 X11 和 XShm。原始画面在内存中编码成质量 75 的 JPEG，再拆成开始包、多个数据块和结束包，通过 TCP 发送。客户端在后台线程组帧和解码，只把最新可用画面交给界面绘制；反方向则发送鼠标和键盘事件，由服务端注入系统。

> 控制协议还包含心跳和自动重连。空闲三秒发起心跳，十秒未收到数据判定断线；客户端按一、二、四、八秒退避重连。

## 1:05–2:15｜现场演示

画面：被控端服务端窗口、控制端 Qt 客户端。

操作与口播：

1. 展示服务端已监听 `9999`，在客户端输入被控端 IP 并连接。

   > 连接后，客户端会显示远端分辨率、当前帧大小、丢弃帧数和心跳往返时间。

2. 改变客户端窗口大小。

   > 这里可以看到画面始终保持原始宽高比。多出来的区域留黑边，鼠标坐标只在真实画面区域中换算，避免窗口拉伸后点击偏移。

3. 在远端打开的记事本中点击，输入 `remote-control-demo`，按 Backspace、Enter。

   > 鼠标支持移动、按下、释放、单击、双击和滚轮；键盘分别传输按下和释放，而不是只传一个字符，所以组合键的模型也更完整。

4. 取消输入开关后再点击，随后恢复开关。

   > 关闭输入时客户端会先释放已经记录的按键和鼠标按钮，避免远端留下按键卡住的状态。画面传输不受影响。

## 2:15–3:15｜最花时间的功能

画面：依次展示 `common/packet.h`、`windows/server.cpp`、`windows/qt_client/connection_window.cpp`，不要长时间滚动。

口播：

> 最花时间的不是建立 TCP 连接，而是让连续屏幕帧在网络波动下仍然可用。TCP 是字节流，没有应用层消息边界，一张 JPEG 也经常大于单个数据包，所以我设计了固定十二字节包头，并用 frame id、offset 和长度把一帧拆成多个不超过约 64 KiB 的块。客户端只有收齐同一个 frame id 的开始、数据和结束消息才解码，残缺帧直接丢弃。

> 另一个关键点是延迟控制。如果解码速度落后于接收速度，排队显示每一帧会让画面越来越旧。因此解码忙时只保留一个最新待处理帧，新帧覆盖旧帧。我选择牺牲部分连续性，换取操作时看到的画面更接近当前状态。

## 3:15–4:05｜最细致的设计

画面：展示 `windows/qt_client/remote_screen_widget.cpp` 与 Qt 客户端画面。

口播：

> 我处理得最细的是输入坐标和输入状态。客户端按比例缩放后，真实画面可能带黑边，所以坐标换算要先扣除绘制区域偏移，再按远端分辨率映射，并拒绝黑边上的输入。鼠标移动还做了重复点抑制和发送节流。

> 对键盘和鼠标按钮，我在客户端记录按下状态。当窗口失去焦点、断线、关闭输入或退出时，会补发释放事件。这类细节界面上不显眼，但如果没做，远端很容易出现 Ctrl、Shift 或鼠标按钮一直按住的问题。

## 4:05–4:35｜工程稳定性

画面：回到架构图右下角，或展示 Qt 状态栏。

口播：

> 工程层面还做了心跳超时、指数退避重连、套接字 RAII 以及发送互斥。发送互斥很重要，因为画面线程和心跳线程可能同时写同一个 TCP 连接；不加保护时，不同消息的字节可能交错，接收端就会读到损坏的包头。

## 4:35–4:55｜遗憾与下一步

画面：仓库 README 的限制部分，或继续显示架构图。

口播：

> 目前最大的遗憾是它仍是工程原型。协议还没有认证和加密，画面使用完整 JPEG 帧，带宽和 CPU 效率不如视频编码；Linux 输入也主要面向 X11。下一步我会先给协议增加版本、认证和 TLS，再研究差分区域或 H.264 编码，并补上多显示器和剪贴板支持。

## 4:55–5:00｜结束

> 这个项目让我真正把平台 API、网络协议、并发和交互细节放进了同一个可运行系统。我的介绍结束，谢谢。

## 追问备忘（不放进五分钟正文）

- 为什么选择 TCP：屏幕帧和输入命令都需要有序、可靠到达；这个原型优先保证正确性和实现闭环。若追求更低延迟，可研究 QUIC 或将画面与控制拆成不同通道。
- 为什么 JPEG 质量是 75：在清晰度、编码成本与帧大小之间做的工程折中；没有声称它是全场景最优值。
- 为什么丢帧：远程控制更关心“新鲜度”而不是每帧必达显示；旧帧排队会增加操作反馈延迟。
- 是否能公网使用：技术上可通过端口映射或隧道连接，但当前没有认证和加密，不建议暴露到不可信公网。
- 为什么不是成品远控软件：当前目标是验证跨平台捕获、传输、显示、输入和断线恢复的完整链路。
